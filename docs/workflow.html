Budget and price — what this snapshot can and cannot say

There is no verified price in this snapshot

A registry row carries a cost class — $0, per-job or subscription — never a price anyone has verified. The only verified-price object in the repo is PriceEntry in src/lib/apex/cost.ts, and it needs verifiedFrom plus verifiedOn before a number exists. Neither appears in this data file.

The verdict the code already prints

judgeBudget() in src/lib/apex/cost.ts is a binary gate: withinBudget is true only when unknownPrices is empty. While it is not empty the advice is this line, verbatim from the source:

“… tools have no verified price — the quote is incomplete, not expensive”

Unpaid local work is a separate, measured fact: the rows below are the count of catalogued tools whose cost class is $0, and the count that runs on your own machine. Neither is a quote for a finished minute.

The only prices this repo holds as code, not copy, are $0 for a seal, $0 for verification and $0 for a receipt export — FREE_FOREVER, src/lib/apex/psi.ts. Verification is free forever and is never the paid lock.

Run the pipeline — the real door, and why this page does not open it

What runStage() actually does, in code order

Read from src/lib/apex/orchestrate.ts, line by line, then cross-checked against src/lib/apex/drivers/contract.ts. One candidate tool at a time, in the stage's preference order:

    Where the door is

    The function is runStage(drivers, input, intent, hooks) in src/lib/apex/orchestrate.ts. Its callers live in the operator app in this repo — /create (one run) and /director (the ten stages) — which reach it through buildDrivers() and stageRoutes() in src/lib/apex/drivers/index.ts.

    Today runStage() has no production caller in this repo. The only file that calls it is the self-check, scripts/apex-check.mjs. That is a fact about the build, not a bug in this page.
    This static site has no runner, no Node process, no shell access and no database. A button here could only animate. It would be a lie with a progress bar, so there is no button — the plan is printed and the door is named instead.

    The two states a stage can honestly end in

    The StageRun object answers four questions: who produced it, what it cost, how long it ran, what came out.
    StateMeansWho is holding the film
    succeededA driver ran and returned outputs; the loop stopped.Nothing to do — the file exists.
    needs-humanFile-exchange depth: a handoff was issued, no run happened.The operator opens the app and does the click.
    failedCandidates were tried and none produced the artefact.The attempt log is the deliverable; it is kept verbatim.
    no-driverThe stage's tool list was empty. It is reported, never skipped.That is dialogue today.

    What the run writes afterwards

    Every finished run — success or not — goes through hooks.onLedger then hooks.onMemory. Failed attempts are, in the file's own words, “the most valuable rows in the whole system”. A seal records that a statement was made; it never proves the statement true. The ledger tables those hooks would write to are drafted and not yet applied — see the operator console.
